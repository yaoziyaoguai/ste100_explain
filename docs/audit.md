# 需求覆盖与发布审计

## 当前目标

将原 `explain` 审计修订为 `ste100_explain`，以本仓库维护源文件，在 Codex 和 Claude Code 安装同一版本，并提交到既有 GitHub 远端。原来的 `explain` 安装在新版本验证后移除。

## 对照最初需求

依据是用户提供的原始文字，未推测其作者。原文希望模型承担更多制作工作，用清晰文字、图、交互网页和自定义讲解视频降低理解与监督成本。

| 原始要求 | 审计发现 | 本次处理 |
| --- | --- | --- |
| 用 ASD-STE100 改善文字可读性 | 初版仅有一般写作原则 | 保留并明确八项默认约束、规则依据与改写示例 |
| 可以使用“80% STE”软化风格 | 后续版本提到该说法，但未给行为分支 | 新增明确的文风强度切换，事实与条件约束仍保留 |
| 用图或图片帮助理解 | 已有工具选择，成品边界较弱 | 明确实际图示交付、编辑源与渲染检查 |
| 用 HTML 制作漂亮、交互式解释 | 偏向小型演示和技能转交 | 明确独立页面、预览、交互验证和视觉层级；允许任务所需的多个视图 |
| 任意主题的自定义视频、3b1b 式视觉讲解 | 更偏数学工具入口，易停在分镜 | 补充非数学主题、场景编排、代表片验证和完整成片交付 |
| 使用 ElevenLabs，或寻找本地免费旁白 | 有笼统 TTS 建议 | 加入指定服务优先、已有授权复用、本地能力检查与声音样本验证 |
| 模型承担制作，用户侧重监督和理解 | 有效果目标，缺少明确的执行边界 | 明确读材料到验证的完整工作，以及可检查的假设和证据 |
| 可以生成较大、定制、一次性的软件产物 | “足够用”和“小型”容易限制尝试 | 按理解任务决定规模，允许较大的解释工具，避免无关产品设施 |

## 安装与名称

- 技能名、目录名和仓库名统一为 `ste100_explain`，遵循用户明确要求。
- 现有仓库的远端为 `https://github.com/yaoziyaoguai/ste100_explain.git`，审计开始时为空仓库，已有可见性为 public；沿用原配置。
- 两端安装使用指向本仓库的符号链接，避免副本漂移。
- 通用 `skill-creator` 校验器只接受连字符命名。不得把其命名失败记录为通过；下划线名称需要另做真实宿主发现检查。

## 第二轮审计

重新对照上表、技能正文、参考文件和实际安装结果，修复了以下问题：

1. 将 UI 显示名称也统一为 `ste100_explain`，避免只改目录与 frontmatter。
2. 修复 README 的裸 `ln -s` 用法：显式检查现有路径和失效链接，防止嵌套安装或覆盖已有内容，并执行了四种安装场景。
3. 将真实宿主发现与通用命名规范检查分开记录；保留下划线名称，确认两端实际接受。
4. 保留原有 STE 八项约束，同时补齐文风强度、独立 HTML、非数学视频、指定或本地旁白，以及一次性解释工具的完整交付。

原始要求在指令和交付约定中均有对应条目。后续需要通过实际制作任务继续验证网页、图像、视频与配音质量；这些是明确保留的验证边界，不是已经通过的测试。
